# TDD в Agent Office

Для новой фичи или багфикса сначала пишется тест, потом код.

## Цикл

1. **Red.** Тест в `tests/test_server.py` описывает ожидаемое поведение. Для бага он воспроизводит баг. Запустить и убедиться, что он падает, причём по нужной причине.
2. **Green.** Минимальный код, с которым тест проходит. Ничего сверх него.
3. **Перед `git push`.** Полный прогон. Если хоть один тест красный, не пушить.

```bash
npm test            # тесты сервера (unittest), зависимости не нужны
npm run check       # типы TypeScript в src/
```

Один тест:

```bash
python3 -m unittest tests.test_server.CodexUsageTest -v
```

## Тест не подгоняется под код

Упал тест: сломана логика, чинить надо её. Менять тест можно только в двух случаях:

1. Пользователь явно сказал, что поменялись требования к поведению. Сначала правится тест, потом код.
2. Тест ссылается на то, чего больше нет: функция удалена, переименована, флоу переработан. Прежде чем править, убедиться, что изменение в коде намеренное, а не регрессия.

## Когда test-first не нужен

- Правка без логики: опечатка, переименование, форматирование, тексты.
- Только документация.
- Одноразовый эксперимент, который не идёт в PR.
- Отрисовка в `src/floors.ts` и `src/menubar.ts`: для неё тестового фреймворка нет. Вместо теста `npm run check`, сборка и проверка в браузере, см. скил `verify-done`.

## Как здесь пишутся тесты

Сервер читает журналы с диска, поэтому тест собирает маленький журнал во временной папке и проверяет результат разбора. В `tests/test_server.py` уже есть помощники: `line`, `rec`, `meta`, `context`, `event`, `usage_record`. Новые тесты строятся на них.
